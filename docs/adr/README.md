# 공용 ADR 가이드

ADR(Architecture Decision Record)은 중요한 결정의 배경과 근거를 보존하는 기록이다. 무엇을 결정했는지뿐 아니라 어떤 대안을 검토했고 어떤 제약을 감수했는지 남긴다.

## 위치와 문서의 역할

- 원본: 저장소의 `docs/adr/`. 프런트엔드·백엔드·인프라가 공용 목록과 번호를 사용한다.
- 위키: 이 가이드나 개별 ADR의 링크를 제공한다. 원문을 복제하지 않는다.
- 이슈: 작업 범위, 완료 기준, 후속 작업을 추적하고 ADR을 연결한다.
- 설계·구현 문서: 상세 API, 스키마, 구현 절차를 설명하고 결정 근거는 ADR을 참조한다.
- 댓글: 논의 과정을 남긴다. 결론과 근거는 ADR에 요약한다.

[작성 템플릿](template.md)을 복사해 사용한다. 루트 [AGENTS.md](../../AGENTS.md)는 에이전트의 작성 규칙을 정의한다.

## 언제 작성하는가

이후 개발이나 운영에 영향을 주거나, 되돌리는 데 비용이 드는 결정을 기록한다. 예를 들어 계정·권한 경계, 인증 방식, 데이터 저장 구조, API 호환 정책, 기술 선택, 배포 경계가 해당한다.

단순 버그 수정, 이름 변경, 포맷 정리, 이미 승인된 설계를 그대로 구현하는 작업에는 새 ADR이 필요하지 않다. 규모가 작더라도 기존 결정을 변경한다면 기록한다. 여러 독립된 결정은 나누되, 하나의 결정을 이해하는 데 필요한 내용을 억지로 분리하지 않는다.

## 이름과 메타데이터

- 파일명: `NNNN-kebab-case-title.md`. 예: `0001-account-role-boundary.md`.
- 번호: 목록과 파일의 기존 최대 번호 다음 번호를 사용한다. 최초 번호는 `0001`이며 삭제·기각된 번호도 재사용하지 않는다. 병렬 작업에서 번호 충돌이 생기면 병합 전에 조정한다.
- 영역: `공통`, `백엔드`, `프런트엔드`, `인프라` 중 필요한 항목을 표시한다. 별도 영역별 번호를 만들지 않는다.
- 날짜: `YYYY-MM-DD`. 결정일은 실제 승인 시점이며, 제안 상태에서는 `미정`으로 둔다.
- 승인 근거: 명시적 합의가 담긴 이슈 댓글·PR·회의 기록 등을 연결한다. 대화에서 합의했고 링크가 없다면 합의 날짜와 내용을 요약하며 링크나 승인자를 꾸며내지 않는다.
- 관련 자료나 대체 관계가 없으면 `없음` 또는 `해당 없음`으로 표시한다. 미확정 값은 `미정`과 확인할 내용을 적는다.

## 상태와 변경 절차

| 상태 | 의미 |
|---|---|
| 제안 | 논의 중이며 아직 승인되지 않음 |
| 승인 | 명시적으로 합의된 결정. 구현 완료를 의미하지 않음 |
| 기각 | 검토했으나 채택하지 않은 제안 |
| 폐기 | 제안이 철회됐거나, 기존 결정이 더 이상 적용되지 않음. 사유와 근거 기록 |
| 대체됨 | 새로 승인된 ADR이 이전 결정을 대체함 |

1. 관련 ADR과 이슈를 읽고 중복·충돌을 확인한다.
2. 템플릿을 복사하고 번호·영역·상태를 정한다. 합의 전에는 `제안`, 이미 명시적으로 합의된 내용은 근거와 함께 `승인`으로 기록한다.
3. 배경 → 대안과 논의 → 결정 → 영향 → 미결 사항 순서로 작성한다. 실제로 검토한 대안만 기록하고, 가능한 경우 선택하지 않은 이유도 설명한다.
4. 공유 API·화면·운영에 영향을 주는 경우 관련 담당자가 검토할 수 있도록 PR 또는 이슈에 ADR을 연결한다. 에이전트는 별도 지시 없이 알림이나 댓글을 게시하지 않는다.
5. 합의가 이루어지면 상태·결정일·승인 근거와 아래 목록을 함께 갱신한다. 이미 확보한 합의를 다시 승인받기 위한 절차는 만들지 않는다.
6. 구현과 후속 작업은 이슈·PR로 추적한다. 미결 사항은 가정과 구분하고, 이번 결정에 영향을 주는지와 확인할 작업을 적는다.

승인된 결정의 의미를 바꾸는 경우 새 ADR을 작성한다. 새 문서가 승인되기 전에는 이전 결정을 `대체됨`으로 바꾸지 않는다. 승인 후 새 문서에는 대체하는 ADR을, 이전 문서에는 대체한 ADR을 연결하고 목록도 수정한다. 기존 배경·결정·근거는 보존한다. 단순 오탈자와 링크 수정은 같은 파일에서 처리할 수 있다. 대체 없이 폐기하는 경우에도 명시적인 근거와 적용 종료 내용을 남긴다.

## 작성 요령

- 대화록 전체 대신 결정에 영향을 준 논점을 요약한다.
- 확정 사항, 제안, 가정을 섞지 않는다. 가정은 아직 검증되지 않았음을 표시한다.
- 장점뿐 아니라 감수하는 제약과 위험을 적는다.
- 아직 모르는 모든 것을 나열할 수는 없다. 현재 파악한 미결 사항과 추가 검토 항목을 기록한다.
- 비밀번호, 토큰, 초기 설정 코드, 개인정보 등 비밀정보를 넣지 않는다.
- 해당하는 내용이 없으면 `없음` 또는 `해당 없음`으로 표시한다. 빈칸을 채우려고 사실을 만들지 않는다.

## 짧은 작성 예시

> 아래는 형식을 보여주기 위한 가상 예시다. 실제 프로젝트의 승인된 결정이 아니며 ADR 번호와 목록에 등록하지 않는다.

- 제목: 외부 조회 실패 시 화면의 재시도 방식
- 상태: 제안
- 영역: 공통
- 작성일: 2026-11-14
- 결정일·승인 근거: 미정
- 배경과 문제: 자동 재시도가 요청을 늘리고, 사용자는 진행 여부를 알기 어렵다.
- 검토한 대안과 논의: 자동 재시도는 편리하지만 요청이 늘어난다. 수동 재시도는 사용자의 조작이 필요하지만 호출 시점이 명확하다.
- 결정안: 화면에 오류와 재시도 버튼을 제공한다. 아직 승인된 정책은 아니다.
- 결과와 영향: 중복 호출을 줄일 수 있지만 일시적 장애에도 사용자가 다시 눌러야 한다.
- 미결 사항과 가정: 시간 초과 기준과 접근성 안내를 추가 검토한다. 후속 이슈는 아직 없다.

## 검토 체크리스트

- [ ] 실제 논의·합의에 근거하며 제안과 승인을 구분했는가?
- [ ] 배경, 대안과 논의, 결정, 영향, 미결 사항과 가정이 구분되는가?
- [ ] 상태·날짜·영역·승인 근거·대체 관계가 정확한가?
- [ ] 관련 링크가 유효하고 비밀정보가 없는가?
- [ ] 번호가 중복되지 않고 목록이 문서 상태와 일치하는가?
- [ ] 구현 완료와 결정 승인을 혼동하지 않았는가?
