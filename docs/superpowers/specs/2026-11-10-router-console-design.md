# 내부 팀용 LLM Router 통합 콘솔 기획·설계

- 작성일: 2026-11-10
- 상태: 대화에서 합의한 요구사항을 정리한 초안. 설계 제안과 미확정 사항은 별도 표시한다.
- 목적: 구현 계획의 기준이 되는 제품 범위와 운영 정책을 정의한다.
- 이 문서는 기능 구현이나 배포 완료를 의미하지 않는다.

## 1. 제품 목표

내부 팀이 여러 LLM 제공업체를 하나의 Router로 사용하고, 프로젝트별 API 키·요청 기록·사용량·예산을 통합 관리한다. 일상적인 키 관리와 장애 확인에 사용할 수 있는 관리 콘솔을 제공한다.

첫 실제 사용처는 팀이 함께 사용하는 하나의 Open WebUI이며, 첫 버전은 텍스트 대화를 대상으로 한다. 채팅 화면은 Open WebUI가 담당하고 Router는 호출 중계와 관리 콘솔을 담당한다.

프로젝트는 서비스·팀·용도 등 사용자가 자유롭게 정하는 관리 단위다. Open WebUI 사용자나 대화방을 프로젝트에 강제로 매핑하지 않는다. 요청의 귀속 프로젝트는 인증에 사용한 Router 키로 결정한다. 하나의 키를 공유한 호출을 자동으로 개인별 사용량으로 분리하지 않는다.

### 성공 기준

팀원이 초대받아 로그인하고, 허용된 프로젝트에서 자신의 역할에 맞는 작업을 수행할 수 있다. 프로젝트 관리자는 키를 발급해 Open WebUI에 연결하고, 실제 대화 이후 요청 상세와 사용량·추정 비용을 확인할 수 있다. 설정한 예산 정책과 키 폐기가 실제 호출에 반영된다.

### 첫 버전의 비목표

- 외부 고객 대상 공개 가입, 결제·크레딧 판매
- 별도의 채팅 서비스 개발
- 이미지·파일·오디오 입력
- 소셜 로그인과 외부 알림 채널
- 자동 모델 선택, 장애 시 대체 모델 호출, 응답 캐시
- 프로젝트 전용 제공업체 연결과 프로젝트별 모델 허용 목록 UI

기존 도구 호출 기능은 유지한다. 다만 첫 사용 검증의 중심은 텍스트·스트리밍·다중 턴 대화다.

## 2. 현재 기반과 개발 접근

현재 저장소에는 Spring Boot 기반 Router, Chat Completions 및 Responses 수신 API, OpenAI·Anthropic 어댑터, 설정 기반 API 키 인증이 있다. 현재 인증은 키의 유효성을 검사하며, 프로젝트별 계정·관리·통계 기능은 이 기획의 신규 범위다. Gemini 어댑터도 별도 개발이 필요하다.

### 검토한 접근

| 접근 | 장점 | 부담 |
|---|---|---|
| 기존 Router 서버에 관리 API와 영구 저장소를 추가하고 관리 화면 연결 | 기존 호출 경로 재사용, 배포와 운영 단순화 | 기록·관리 작업이 호출 처리에 영향을 주지 않도록 내부 책임 구분 필요 |
| 호출 서버와 관리 서버를 별도 배포 | 독립 확장과 장애 격리 | 인증·설정 동기화 및 기록 전달 구조와 운영 복잡성 증가 |

**설계 제안:** 첫 번째 접근을 기본으로 작성한다. 호출 처리, 인증·권한, 프로젝트 관리, 기록·집계, 알림을 내부 모듈로 구분한다. 사용자는 직전 제안을 바탕으로 문서화를 요청했으며, 세부 기술 구성까지 확정한 것은 아니다. DB 종류, 프런트엔드 프레임워크, 배포 구성은 구현 계획 전에 정한다.

## 3. 확정 요구사항

### 3.1 계정과 팀

- 내부 팀용 콘솔로 운영한다.
- 첫 로그인 방식은 자체 이메일·비밀번호 계정이다.
- 소셜 로그인은 사용 흐름이 자리 잡은 뒤 추가한다.
- 일반 팀원은 접근이 허용된 프로젝트만 확인할 수 있다.
- 전체 관리자가 부여하는 별도의 프로젝트 생성 권한을 둔다. 모든 팀원에게 자동으로 부여하지 않는다.
- 프로젝트 관리자는 이미 등록된 팀원을 자신의 프로젝트에 직접 추가할 수 있다.

**설계 제안:** 공개 회원가입 없이 전체 관리자가 이메일로 초대한다. 초대 수락 시 비밀번호를 설정하고 이메일로 비밀번호를 재설정한다. 최초 전체 관리자는 설치 시 생성한다. 사용자와 로그인 수단을 분리하여 추후 소셜 로그인에도 프로젝트 소속을 유지한다.

### 3.2 권한 모델

팀 전체 권한과 프로젝트별 역할을 구분한다. 프로젝트 생성 권한은 다른 프로젝트 열람 권한이나 공용 연결 관리 권한을 부여하지 않는다.

| 기능 | 전체 관리자 | 해당 프로젝트 관리자 | 해당 프로젝트 조회자 |
|---|---|---|---|
| 프로젝트 정보·통계 조회 | 모든 프로젝트 | 가능 | 가능 |
| 요청·응답·도구·오류 상세 조회 | 모든 프로젝트 | 가능 | 가능 |
| 키 목록·용도·상태 조회 | 모든 프로젝트 | 가능 | 가능 |
| Router 키 발급·폐기 | 가능 | 가능 | 불가 |
| 프로젝트 예산·차단 정책 변경 | 가능 | 가능 | 불가 |
| 기존 팀원을 프로젝트에 추가 | 가능 | 가능 | 불가 |
| 공용 제공업체 연결 관리 | 가능 | 불가 | 불가 |
| 팀 전체 예산 상한 변경 | 가능 | 불가 | 불가 |
| 팀원의 프로젝트 생성 권한 관리 | 가능 | 불가 | 불가 |

**설계 제안:** 프로젝트 생성자는 해당 프로젝트 관리자가 된다. 프로젝트 관리자는 멤버 제외와 역할 변경도 수행한다. 마지막 관리자를 제거하려면 다른 관리자에게 역할을 넘겨야 한다. 생성 권한 회수는 이후 생성만 막고 기존 프로젝트 역할은 별도로 관리한다. 프로젝트 접근 회수는 과거 기록에도 적용한다.

권한 검사는 화면 표시뿐 아니라 모든 관리 API, 상세 조회, 검색, 통계, 내보내기에 적용한다. 접근할 수 없는 프로젝트의 데이터가 전체 집계에 섞여 노출되지 않게 한다.

### 3.3 키와 제공업체 연결

- 제공업체 API 키는 팀 공용으로 사용한다.
- Router API 키는 프로젝트별로 발급하고, 하나의 키는 하나의 프로젝트에 소속한다.
- 조회자는 키 목록과 용도를 확인하고 요청에 사용된 키를 식별할 수 있다. 키 원문 접근과 발급·폐기는 불가하다.
- 키 발급·폐기는 전체 관리자와 해당 프로젝트 관리자만 수행한다.
- 프로젝트별 제공업체 연결은 향후 확장 가능하도록 고려한다.

**설계 제안:** Router 키 원문은 발급 직후 한 번만 표시하고 이후에는 재조회하지 않는다. 이름·설명·식별용 접두사·상태·생성일·만료일·마지막 사용 시각을 제공한다. Router 키는 검증용 해시로 저장하고 제공업체 자격 증명은 서버 호출에 필요한 방식으로 암호화해 보관한다. 인증 헤더와 키 원문은 로그·요청 기록·내보내기에 저장하지 않는다.

공용 제공업체 연결은 프로젝트와 독립된 개념으로 둔다. 후속 확장 시 프로젝트 전용 연결이 있으면 그것을 사용하고, 없으면 공용 연결을 사용하도록 제안한다. 원본 입력·출력의 토큰 문자열까지 무조건 비밀정보가 없다고 보장하는 것은 아니며, 본문 마스킹 정책은 추가 결정 사항이다.

### 3.4 모델 접근

- 첫 버전은 등록된 활성 모델 전체를 사용할 수 있다.
- 새로 등록한 활성 모델도 기본적으로 사용 가능하다.
- 향후 `전체 허용`과 `지정 모델만 허용` 정책을 지원할 수 있게 한다.
- 후속 제한 정책은 모델 목록 조회와 실제 호출에 동일하게 적용한다.

모델이 등록되어 있어도 해당 모델이 지원하지 않는 API나 입력 형식을 지원하는 것으로 취급하지 않는다. 현재 모델별 API 지원 검증은 유지한다.

### 3.5 요청 기록

문제 발생 시 입력부터 변환·업스트림 처리·출력까지 확인할 수 있어야 한다. 조회자는 자신에게 허용된 프로젝트의 본문도 열람할 수 있다.

| 기록 영역 | 저장할 내용 |
|---|---|
| 식별·귀속 | Router 요청 ID, 프로젝트, Router 키 식별자, 호출 시각, 수신 API 경로 |
| 클라이언트 입력 | 메시지·지시문, 도구 정의, 요청 모델과 생성 옵션 |
| 제공업체 송신 | 실제 연결·모델, 변환 후 요청 본문 |
| 제공업체 응답 | 수신 본문, 도구 호출·인자, 제공된 사용량과 요청 ID |
| 클라이언트 출력 | 최종 반환 본문과 상태 |
| 스트리밍 | 수신·송신 이벤트 순서와 시각, 누적 출력, 중단 지점 |
| 오류·성능 | 오류 코드·내용, 성공·실패·취소 상태, 전체 지연, 첫 응답까지의 시간 |
| 비용 | 입력·출력·캐시 등 사용량 구분, 계산 근거와 추정 비용 |

실패·취소·중간 중단도 확보한 범위까지 기록한다. 내용이 잘렸거나 일부 저장에 실패했다면 완전한 기록처럼 표시하지 않는다. 클라이언트 내부의 도구 실행 과정은 관찰할 수 없으며, Router가 받은 도구 실행 결과만 기록할 수 있다.

**설계 제안:** 별도 추적 ID로 여러 요청을 하나의 작업에 연결할 수 있게 한다. 요청 ID와 추적 ID는 대화 전체가 자동으로 식별된다는 의미가 아니다. 요청 본문 열람과 관리 변경에는 감사 기록을 남긴다.

### 3.6 보관과 통계

- **확정:** 요청·응답 상세 본문과 스트리밍 이벤트는 30일 보관 후 자동 삭제한다.
- **설계 제안:** 본문을 제외한 요청 요약·사용량·비용은 1년 보관한다. 감사 기록의 보관 기간은 별도로 결정한다.
- 오류 메시지, 도구 인자, 파생 데이터와 내보내기 사본 등 본문이 포함될 수 있는 저장 위치도 보관 정책에 포함한다.
- 프로젝트·키·제공업체·모델·기간별 요청 수, 토큰, 추정 비용, 오류와 지연을 조회하는 통계를 제안한다.
- 통계는 Router를 통과한 요청을 대상으로 한다. 제공업체에 직접 보낸 호출은 자동 집계되지 않는다.
- 사용량을 받지 못한 경우 `0`이 아니라 `미확인`으로 구분한다.
- 추정 비용과 실제 제공업체 청구액을 구분한다. 호출 당시 적용 단가와 계산 근거를 보관해 단가 변경으로 과거 기록이 달라지지 않도록 한다.

### 3.7 예산과 차단

| 구분 | 설정 권한 | 상한 도달 시 동작 |
|---|---|---|
| 프로젝트 월 예산 | 전체 관리자·해당 프로젝트 관리자 | 알림만 또는 새 호출 차단 중 선택 |
| 팀 전체 월 예산 상한 | 전체 관리자 | 모든 프로젝트의 새 호출 차단 |

- 프로젝트 예산 모드는 두 가지 모두 지원한다.
- 팀 전체 상한은 프로젝트 정책보다 우선한다. 프로젝트 예산을 늘리거나 알림 모드로 바꿔도 전체 상한을 우회할 수 없다.
- 조회자는 예산·정책·사용 현황을 확인할 수 있지만 변경할 수 없다.
- 변경자·시각·이전 값·새 값을 기록한다.

**설계 제안:** 진행 중인 요청은 마무리한다. 예산 증액이나 다음 월 예산 기간 시작 시 재개한다. 한국 시간 기준 매월 1일 기간을 새로 시작하고 비용 단위는 USD로 한다. 기록을 삭제하는 방식으로 월 사용량을 초기화하지 않는다.

추정 비용과 진행 중 요청 때문에 실제 지출이 상한을 일부 초과할 수 있다. 엄격한 금액 보장이 필요하면 요청 전 비용 예약·정산 방식이 필요하므로 구현 전에 결정한다. 사용량 미확인 요청의 예산 반영 방식도 미확정 사항으로 둔다.

### 3.8 알림

- **확정:** 콘솔 내 알림과 이메일을 제공한다. Slack 등 외부 채널은 후속 확장한다.
- **설계 제안:** 프로젝트 예산 알림은 프로젝트 관리자, 전체 예산 알림은 전체 관리자에게 보낸다. 전체 상한에 따른 차단은 영향을 받는 프로젝트 관리자에게도 알린다.
- **설계 제안:** 월 예산 80%·100% 도달 시 알림을 보내고 같은 기간·대상·임계치의 중복 발송을 방지한다.
- 콘솔에서 발생 시각·원인·대상과 읽음 상태를 확인하도록 제안한다. 이메일 실패와 재시도는 호출 처리와 분리한다.

## 4. 관리 콘솔 구성 제안

| 메뉴 | 핵심 기능 |
|---|---|
| 개요 | 접근 가능한 범위의 사용량·비용·오류·예산 현황 |
| 프로젝트 | 목록, 생성, 정보, 멤버, 예산 설정 |
| API 키 | 프로젝트별 목록·용도·상태, 관리자 발급·폐기 |
| 요청 이력 | 기간·프로젝트·키·모델·상태 검색, 변환 전후 본문과 이벤트 상세 |
| 사용량·비용 | 기간별 추이와 프로젝트·모델·키별 집계, 내보내기 |
| 알림 | 예산·차단 알림과 읽음 상태 |
| 팀 관리 | 전체 관리자의 초대·계정 관리·생성 권한 관리 |
| 제공업체·모델 | 전체 관리자의 공용 연결과 모델 등록·활성 상태 관리 |
| 감사 기록 | 관리 변경과 본문 열람 기록 |

이 목록은 화면 설계 제안이며 UI 배치와 구체적인 검색 필드까지 확정한 것은 아니다. Router 자체 테스트 도구는 Open WebUI 연결 검증 이후의 추가 후보로 둔다.

## 5. 데이터와 처리 책임 제안

핵심 데이터는 사용자, 로그인 수단, 프로젝트, 프로젝트 멤버, Router 키, 제공업체 연결, 모델, 요청, 업스트림 시도, 상세 본문·이벤트, 사용량·비용, 예산 정책, 알림, 감사 기록이다.

- 요청은 프로젝트·키에 귀속시키고, 키 폐기 후에도 과거 요청의 귀속을 보존한다.
- 요청과 업스트림 시도를 구분할 여지를 두어 향후 재시도 시 이중 집계와 추가 비용을 구별한다.
- 본문·이벤트와 장기 요약을 분리해 30일 삭제 후에도 집계를 유지한다.
- 예산 검사와 사용량 반영은 동시 요청을 고려한다. 완료한 요청의 사용량이 중복 반영되지 않아야 한다.
- 기록·집계·알림의 책임을 호출 변환 로직과 분리한다. 저장 실패가 발생했을 때의 호출 허용 정책은 구현 전에 정한다.
- 요청/키 관리 상태와 실제 호출 경로가 일치해야 한다. 폐기된 키와 회수된 권한이 캐시에 무기한 남지 않도록 한다.

## 6. 단계별 구현 범위 제안

### 1단계: 계정·프로젝트·키와 실제 호출

영구 저장소, 초기 관리자, 초대·로그인·비밀번호 재설정, 프로젝트 생성 권한, 멤버 역할, 프로젝트별 Router 키 인증을 구현한다. Open WebUI에서 모델 조회·스트리밍·다중 턴 텍스트 대화를 확인한다.

### 2단계: 요청 기록과 운영 조회

변환 전후 요청·응답과 스트리밍을 기록하고, 관리 화면에서 검색·상세 조회한다. 30일 삭제, 장기 요약, 사용량·추정 비용 집계와 감사 기록을 추가한다.

### 3단계: 예산·알림과 관리 콘솔 완성

프로젝트 예산의 두 모드, 전체 상한, 콘솔·이메일 알림, 공용 연결·모델 관리를 완성한다. 권한과 비용 통제를 포함한 전체 사용 흐름을 검증한다.

세 단계는 첫 버전을 완성하기 위한 개발 순서다. 예산과 알림을 첫 버전에서 제외한다는 의미는 아니다.

## 7. 수용 기준

1. 접근 권한이 없는 프로젝트는 목록·검색·상세·통계·내보내기에서 확인할 수 없다.
2. 생성 권한이 없는 팀원은 프로젝트를 생성할 수 없다.
3. 프로젝트 관리자는 기존 팀원을 추가하고 키를 발급·폐기할 수 있다.
4. 조회자는 키의 용도와 요청 본문을 확인할 수 있지만 키 발급·폐기·원문 접근과 설정 변경은 불가하다.
5. 프로젝트 키로 Open WebUI의 모델 목록·텍스트 스트리밍·후속 대화가 동작하고 요청이 올바른 프로젝트에 귀속된다.
6. 정상·실패·취소·중단 요청에서 확보한 입출력과 이벤트를 확인할 수 있다.
7. 상세 데이터는 30일 후 삭제되고 본문 없는 요약은 별도 보관 정책을 따른다.
8. 프로젝트 예산의 알림 모드와 차단 모드가 다르게 동작하며, 팀 전체 차단이 우선한다.
9. 예산 알림이 콘솔과 이메일에 전달되고 동일 임계치의 중복 발송을 방지한다.
10. 사용량 미확인과 0 사용량을 구분하며, 화면의 비용을 추정치로 표시한다.

## 8. 구현 전에 정할 사항

아래는 확정 요구사항이 아닌 후속 결정 목록이다. 확정하지 않은 정책을 사용자 합의로 취급하지 않는다.

- 첫 버전에 Gemini를 포함할지, 기존 OpenAI·Anthropic부터 시작할지
- DB·관리 화면 기술·배포 환경 및 이메일 발송 서비스
- 초대·초기 관리자·비밀번호 재설정의 구체적인 계정 운영 방식
- 요청 요약 1년 보관, 감사 기록 및 백업·내보내기 파일의 보관 기간
- 월 예산의 한국 시간·USD 기준, 80%·100% 알림 기본값
- 비용 산정 대상과 단가 관리, 사용량 미확인 및 진행 중 요청의 예산 처리
- 기록 저장 실패 시 호출 지속 여부, 본문 크기 한도와 마스킹 정책
- 멤버 제외·역할 변경·마지막 관리자 보호의 상세 규칙
- 기존 설정 기반 키의 전환·폐지 방식과 기존 클라이언트 이전 절차

세부 클래스 구성, 내부 인터페이스, 인덱스, 집계·삭제 작업의 구현 방식은 위 정책을 만족하는 범위에서 구현자가 결정한다. 본 문서를 검토한 후 별도 구현 계획으로 구체화한다.
